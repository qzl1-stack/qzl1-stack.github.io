用同一条数据贯穿所有格式，看最直观。

假设要传这条消息：

```
id = 1
name = "Hi"
value = 3.14
```

---

### 文本类：你写什么就是什么

#### JSON

```
{"id":1,"name":"Hi","value":3.14}
```

字符串直接存，每个字符占 1 字节，加上括号冒号引号。**33 字节**，人眼直接看懂。

#### XML

xml

```xml
<msg><id>1</id><name>Hi</name><value>3.14</value></msg>
```

靠标签包裹区分字段，更冗余。**54 字节**。

#### CSV（只适合表格）

```
1,Hi,3.14
```

用逗号分隔，无字段名，双方提前约定列顺序。**9 字节**，但无法嵌套。

---

### 二进制类：每一个 bit 都精打细算

用十六进制展示原始字节，每组 `XX` 是一个字节（0–255）。

#### 自定义结构体

提前定义好：

c

```c
#pragma pack(1)
typedef struct {
    uint32_t id;      // 4字节
    char     name[8]; // 8字节固定
    float    value;   // 4字节
} Msg;                // 共16字节
```

内存里直接就是：

```
id(4B)          name(8B)                  value(4B)
01 00 00 00  |  48 69 00 00 00 00 00 00  |  C3 F5 48 40
      ↑               ↑↑                        ↑
      1           'H' 'i' + 补零填满           3.14的IEEE754表示
```

接收端：`memcpy(&msg, buf, 16)` 直接用。**没有任何解析逻辑**，但字段顺序、大小双端必须完全一致。

---

#### Protobuf — Tag + Varint 变长编码

核心思路：**不传字段名，只传字段编号；小数值用更少字节表示。**

每个字段由两部分组成：

```
[Tag 字节] [Value 字节]
```

Tag 字节 = `(字段编号 << 3) | 类型`，类型只有几种：

- `0` = Varint（整数）
- `1` = 64位固定
- `2` = 变长（字符串/bytes）
- `5` = 32位固定（float）

编码过程：

```
字段1: id=1
  Tag = (1<<3)|0 = 0x08
  Value = Varint(1) = 0x01
  → 08 01

字段2: name="Hi"
  Tag = (2<<3)|2 = 0x12
  Length = 2  → 02
  Value = 'H','i' = 48 69
  → 12 02 48 69

字段3: value=3.14 (float)
  Tag = (3<<3)|5 = 0x1D
  Value = IEEE754(3.14) = C3 F5 48 40
  → 1D C3 F5 48 40
```

最终：

```
08 01  |  12 02 48 69  |  1D C3 F5 48 40      共11字节
```

**关键特性：** 字段号不存在时不占任何字节；字段顺序可以打乱；接收端按 Tag 识别字段，多出来的字段直接忽略，这就是"向后兼容"的来源。

---

#### FlatBuffers — vtable 偏移表，零拷贝

核心思路：**数据直接躺在缓冲区里，不解析，靠偏移表跳转读取。**

内存布局分三块：

```
[vtable] [object data] [字符串等变长数据]
```

vtable 记录每个字段相对于 object 起始的字节偏移：

```
vtable:
  0C 00  ← vtable 自身大小(12字节)
  08 00  ← object 数据区大小
  04 00  ← 字段0(id) 的偏移
  08 00  ← 字段1(name) 的偏移
  0C 00  ← 字段2(value) 的偏移

object data:
  01 00 00 00  ← id=1
  [offset→"Hi"]← name 字符串指针
  C3 F5 48 40  ← value=3.14
```

读 `name` 字段时：查 vtable 第2项偏移 → 跳到对应位置读指针 → 跳到字符串。**全程没有拷贝，没有解析分配**，直接在原始 buffer 上寻址。代价是 vtable 头部有固定开销，小消息反而比 Protobuf 大。

---

#### MessagePack — 带类型前缀的紧凑二进制

核心思路：**就是二进制版 JSON，每个值前面跟一个类型字节。**

类型字节（称为 format byte）决定后面跟几个字节：

```
0x83        ← fixmap，含3个键值对
  A2 69 64  ← fixstr长度2, 'i','d'
  01        ← 正整数 1
  
  A4 6E 61 6D 65  ← fixstr长度4, 'n','a','m','e'
  A2 48 69        ← fixstr长度2, 'H','i'
  
  A5 76 61 6C 75 65  ← fixstr长度5, 'v','a','l','u','e'
  CA C3 F5 48 40     ← float32, 3.14
```

最终：

```
83  A2 69 64 01  A4 6E 61 6D 65 A2 48 69  A5 76 61 6C 75 65 CA C3 F5 48 40
                                                              共约22字节
```

可以看到字段名 `"id"` `"name"` `"value"` 全部内嵌在数据里，所以**不需要任何 Schema 就能解析**，但字段名越长越浪费。实际使用时常把 key 换成数字（`0`,`1`,`2`）压缩体积。

### 总结一张图

```
原始数据：id=1, name="Hi", value=3.14
─────────────────────────────────────────────────────
格式          大小    编码方式
─────────────────────────────────────────────────────
JSON          33B     字符原文 + 分隔符
XML           54B     字符原文 + 标签包裹
自定义结构体  16B     原始内存，直接 cast，无元数据
Protobuf      11B     字段编号+类型Tag + 变长值
FlatBuffers   ~36B    vtable偏移表 + 内联数据，零拷贝
MessagePack   22B     类型前缀 + 字段名字符串 + 值
─────────────────────────────────────────────────────
```

**本质区别只有一条：** 文本格式把"字段名"和"值"都用字符存；二进制格式用编号或偏移代替字段名，值用最紧凑的字节表示。自定义结构体走到极端——连字段描述都不传，双端靠代码约定。
